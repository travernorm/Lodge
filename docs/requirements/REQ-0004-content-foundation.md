# REQ-0004: Content foundation (add content as data, not code)

Status: approved (Traver, 2026-11-03, with the recommended answers). C1 built.

Diagram: [How content flows through Lodge](https://claude.ai/artifact/NcH46fvPgXmHp5k9G48MwN). Roadmap: [Lodge roadmap: scaling up content](https://claude.ai/artifact/L7rZyt2Q5K8m4LpbDp9wXF).

## Problem

Lodge is headed for about 100 fish, several hundred flies and many rivers, but today adding content means editing code:

* **A fly or fish** has to be added by hand to the `flies` or `stocking` list in `fishing_controller.gd` (lines 24 to 33). Nothing finds new files on its own.
* **A species can't live in two rivers.** `FishSpecies.lie_area_m` says where it lives on the one-screen test stream. A `Stretch` lists its trout one by one (`trout: Array[FishSpecies]`), with no count or anything else about how they live there.
* **A new kind of river feature** (undercut bank, plunge pool, riffle) means editing `river_field.gd` (645 lines). Rocks, logs, eddies and gravel are four hard-wired arrays on `Stretch`, each with its own code in the field and in `stream_scene.gd`.
* **Diets are untyped.** `FishSpecies.diet` is a dictionary of insect ids, so a typo shows up only when `data_test` runs, and the inspector shows a text box.

## Player story

As the designer, I want every new fish, fly, insect and river feature to be a data file the game picks up by itself, so content can grow without the code growing with it.

As a player, I get nothing new to see from this REQ. It makes the content waves that follow cheap and safe.

## Feel goals

* No change in play. The demo stretch, its five trout, the fly box and every odd on screen behave the same.
* Adding a fly: make one `.tres` in `data/flies/`, and it shows up in the fly box with no other edit.
* Adding a fish to a river: one line in that stretch's spawn table.
* Adding a boulder or eddy to a river: one line in that stretch's features.
* Adding a new kind of feature: one new script, without touching `river_field.gd`.

## Scope

Three parts, each its own PR, in this order. Field names are proposals for review.

### C1. Catalog

* **`Catalog`** (`scripts/data/catalog.gd`, a `Resource`) lists every archetype by kind: `flies`, `fish`, `insects`, `stretches`. It has `fly(id)`, `species(id)` and `insect(id)` lookups and builds an id index once at load.
* **`data/catalog.tres`** is generated by **`tools/build_catalog.gd`** from the `data/<kind>/` folders. It's an exported list rather than a folder scan, because exported builds rename files to `.remap`.
* **Forgetting to regenerate can't slip through:** `data_test` (run by `tools/run_tests.sh` and CI) fails if the catalog and the folders disagree, and says to run the tool. (Built this way instead of the drafted debug-build folder scan, which R1 rules out for a data script: `OS.` is the wall-clock check. So a new file needs the tool run before it shows up at Cmd+B.)
* **The fly box reads the catalog:** every fly in the catalog, in catalog order. The tool keeps the order between rebuilds and adds new files at the end, so the Parachute Adams stays first. The hard-coded `flies` list leaves `fishing_controller.gd`. Owned flies and a starting kit come later with `FlyBox` (ARCHITECTURE.md step D).
* `tests/data_test.gd` still loads every folder, and also checks the catalog lists exactly those files.

### C2. Kinds vs places

* **`SpawnEntry`** (`Resource`): `species: FishSpecies`, `count: int`. `Stretch.trout` becomes `Stretch.spawn: Array[SpawnEntry]`. Fish take lies from the river field's lie scores over the whole stretch, as the demo already does.
* **Remove `FishSpecies.lie_area_m` and `bite_range_m`.** Nothing reads `bite_range_m` since the landing roll was dropped. After this, a species carries nothing about any place (R12).
* **The one-screen test stream becomes a small stretch** (`data/stretches/test_pool.tres`) with its own spawn table, so there is one way to stock water and the "no stretch" branch in `stream_scene.gd` and `fishing_controller.gd` goes away. The `stocking` list leaves `fishing_controller.gd`.
* **`DietEntry`** (`Resource`): `insect: Insect`, `weight: float`. `FishSpecies.diet` becomes `Array[DietEntry]` with typed insect references (R5).
* Existing fish and stretch files are converted. Nothing is saved yet, so no save migration is needed. Ids don't change.

The hatch table and season windows on a spawn entry are **not** in this REQ. Each field arrives with the system that reads it (the Clock and hatch REQs), so no data sits unused.

### C3. River feature kit

* **`RiverFeature`** (`Resource`, abstract) is one thing on the riverbed. Each kind is a small subclass in `scripts/river/features/`, and each one says how it shapes the water: `shape_depth(p, depth)`, `shape_flow(p, velocity)` and `blocks(p)` for solid things. It also gives its footprint in metres for views to draw.
* Today's four kinds move into it with their current maths: `Boulder`, `Log`, `Eddy`, `GravelBar`. `Stretch.rocks`, `logs`, `eddies` and `gravel` become one `Stretch.features: Array[RiverFeature]`.
* **`RiverField` runs the features in order** and no longer knows any feature by name. This moves the feature maths out of `river_field.gd` and pays down its line cap.
* **Views draw from footprints:** `stream_scene.gd` draws features from their footprints instead of looping over each array, so a new kind needs no view code until it wants its own art.
* **Content waves later add new kinds:** cut bank, undercut, plunge pool, riffle. This REQ adds none.

### Not changing

The rules (`DriftPastRules`, `DriftModel`, `CastModel`, `FightModel`), every number in the data, the input map, the scene tree's nodes.

## Out of scope

* Content sheets (CSV to `.tres` importer). This is a tool, so it doesn't need a REQ. It's built after C2, so its columns match the new `DietEntry` and `SpawnEntry` shapes.
* `FlyBox`, `GameState`, saves (step D's other half), the Clock, hatches, new traits, new feature kinds, new content, art.
* Splitting the HUD and catch card out of `fishing_controller.gd` (step A). C1 and C2 already remove its lists. Step A follows as its own REQ when the first new screen needs it.

## Acceptance criteria

* Adding a valid `.tres` to `data/flies/` and running `tools/build_catalog.gd` puts it in the fly box with no other edit (test: a fixture fly in a temp catalog).
* `run_tests.sh` fails when a data file is missing from the catalog (test).
* No script names a fly or insect file (architecture test, new R5 check, C1). Fish files join the check in C2, when the stocking list goes. Rule set preloads stay, since rule sets are picked by hand (open question 3).
* No `FishSpecies` field describes a place (`lie_area_m` and `bite_range_m` gone, architecture test R12).
* `diet` holds only `DietEntry` with a non-null insect, and the R5 ledger entry for `diet` is removed (architecture test).
* `river_field.gd` names no feature kind, and its R9 cap goes down to its new size (architecture test).
* The demo stretch's baked layers (velocity, depth, seams, lies) match today's within float tolerance (river test against a recorded fixture).
* Every existing test passes unchanged, apart from tests that read the removed fields, which move to the new ones in the same PR and say so.

## Playtest checks

Keyboard and DualSense: cast Short, Middle and Long; cycle every fly with Y/F; land a fish; strike at nothing; reel in; practice mode; F1 read-the-water and the other debug views. It should all feel exactly like today. Browser build: confirm the fly box isn't empty, which proves the catalog works in an export.

## Open questions

Answered by Traver on 2026-11-03: the recommended answer to all three.

1. Is replacing the one-screen test stream with a small test stretch OK? Recommended: yes, since it removes a second code path in two files.
2. Should the fly box show every fly in the catalog until `FlyBox` exists? Recommended: yes for now, then a starting kit with the fly box REQ.
3. Should the catalog list cast rule sets and bite rules too? Recommended: no, they're picked by hand, not browsed.
